# 보일러플레이트 작업 공간 공통 지침

## 1. 작업 공간과 적용 범위

현재 `02.Boilerplates/`는 문서 저장소가 관리하고, 그 아래 두 Composer는 상위 `.gitignore`로 제외한 독립 Git 저장소입니다. 문서 변경은 문서 저장소에서, Composer와 생성 앱 변경은 각각의 저장소에서 관리합니다. 메인 폴더를 Git으로 관리하지 않는 별도 작업 공간에서도 이 구분을 적용합니다. 다음 이름·배치는 예시이며 실제 폴더와 저장소 루트를 확인합니다.

```text
작업공간/                       Git 비관리
├── AGENTS.md                  이 공통 지침
├── typescript-composer/       독립 Git 저장소
│   └── project/생성앱/               Composer에서 제외하는 별도 Git 저장소
├── flutter-composer/          독립 Git 저장소
│   └── project/생성앱/               Composer에서 제외하는 별도 Git 저장소
└── 프로젝트명/                독립 Git 저장소
```

- 메인 폴더에서의 작업은 공통 구조·도구·버전 정책과 요청된 여러 저장소의 변경을 조정하는 용도입니다. 개별 기능 개발은 해당 프로젝트의 규칙과 실행 환경을 기준으로 합니다.
- 사용자 요청을 우선하고 대상 저장소의 AGENTS.md·project-agents.md·README·관리 문서를 함께 읽습니다. 하위 지침은 해당 폴더 범위에 적용하며 다른 저장소의 작업 방식까지 일괄 바꾸지 않습니다.
- 메인 폴더에서 git init을 실행하거나 저장소들을 하나로 묶지 않습니다. 메인 AGENTS.md가 Git 밖에 있다는 이유로 새 저장소·부모 .git·공통 이력 파일을 만들지 않습니다. 보존/공유 방식은 사용자 요청을 따릅니다.
- 공통 업데이트 요청을 모든 프로젝트의 자동 갱신 권한으로 해석하지 않습니다. 적용 대상을 정하고 저장소별로 변경·검증·커밋을 구분합니다. commit·push·배포는 요청된 범위에서만 수행합니다.

## 2. 작업 전 조사·Git 경계

대상 폴더·언어·실행 형태·요청 범위를 먼저 정하고 숨김 설정을 포함해 조사합니다. 적용 지침·Git 상태·manifest/lock·버전 파일·CI·관련 코드/호출자/테스트를 확인합니다. 사용자 변경·삭제를 임의로 복구하거나 커밋에 섞지 않습니다.

Git 명령은 **각 저장소 루트**에서 실행하거나 메인에서 -C로 대상을 명시합니다. 예를 들어:

```bash
git -C ./typescript-composer rev-parse --show-toplevel
git -C ./typescript-composer status --short
git -C ./typescript-composer branch --show-current
git -C ./typescript-composer remote -v
```

실제 대상이 Flutter나 개별 프로젝트면 해당 경로로 바꿉니다. rev-parse 결과가 예상과 다르면 상위 저장소에 잘못 포함됐는지 확인하고 진행합니다. Git 미관리 프로젝트가 있어도 요청 없이 초기화하지 않습니다.

공식 Composer 원본:

- TypeScript: https://github.com/GUuu9/typescript-composer
- Flutter: https://github.com/GUuu9/flutter-composer

실제 remote·브랜치·추적 브랜치를 확인하며 origin/main이나 위 주소를 모든 프로젝트에 강제하지 않습니다. clone한 저장소에 init/remote add를 반복하지 않고 Composer의 .git을 생성 앱에 복사하지 않습니다. Composer 소스를 문서 저장소에 다시 추적시키지 않습니다.

현재 두 Composer의 생성 앱은 해당 Composer의 project/ 아래에 두고 개발합니다. Composer 루트 .gitignore의 고정 규칙으로 생성 앱을 제외하며 compose는 .gitignore를 수정하지 않습니다. 앱의 Git 초기화·커밋·remote는 앱 폴더에서 별도로 수행하며 submodule로 등록하지 않습니다. 이미 추적 중인 파일은 ignore만 추가해도 제외되지 않습니다.

## 3. 작업 유형별 읽기 순서

| 작업 | 먼저 확인할 문서·대상 |
| :--- | :--- |
| 기존 Composer의 base·target·feature 확장 | 해당 저장소 지침 → 관리자 설계/연결 안내 → feature 작성 규칙 → 대상 구성품 README·선언·코드·테스트 |
| 생성/feature 명령·공통 계층 수정 | 해당 지침 → 구조/자동 연결·파일 소유·상태/복구 계약 → 스크립트·회귀 검사 |
| 개별 프로젝트 개발 | 프로젝트 AGENTS/README → 환경/구조 → 해당 기능·빌드/배포 문서·호출자·테스트 |
| 보안·지원·SDK/패키지 업데이트 | 버전 관리/지원 범위 → 공식 권고/릴리스 노트 → 실제 manifest/lock·도구 선택·검증 조합·복귀 |
| 여러 저장소에 공통 변경 | 위 문서 + 대상별 현재 구현/버전 차이·사용자 수정·적용 여부 |
| 기존 프로젝트 추출 | 원본 지침·대표 실행 흐름·버전/테스트 → 보존 범위·독립 샘플 출력 위치 |
| 신규 보일러플레이트 제작 | 목적·언어/플랫폼·단독형/조립형·출력 위치 → 최소 동작·문서·검사 |

문서 경로는 저장소마다 다를 수 있으므로 실제 파일을 찾습니다. 누락되거나 접근하지 못한 내용은 추측하지 않습니다. 기존 Composer 확장은 내부 규칙을 따르고, 새 Composer/생성기 제작은 요청한 경우에만 진행합니다.

## 4. 구현·구조·자동 연결

- 한국어로 설명하고 제품명·파일명·명령은 원래 표기를 유지합니다. 기존 패턴·표준 기능·설치된 의존성을 재사용해 요청을 완결하는 최소 변경을 합니다. 빈 계층·불필요한 옵션/추상화·새 의존성을 추가하지 않습니다.
- 공통 시작/조립은 뼈대·base, 결과 형태/플랫폼 연결은 target, 독립 기능은 feature로 관리합니다. 언어/런타임이 다른 프로젝트에 동일 코드를 기계적으로 복사하지 않습니다. 실제 구현이 없는 계약을 지원된 기능으로 등록하지 않습니다.
- 화면/ViewModel·입출력 Bridge/API·Usecase/Service 등의 기존 책임·의존 방향과 DI 조립·수명 소유를 유지합니다. 외부 입력·IPC 발신자·Origin·경로 검증, 오류 비노출, 비동기 dispose·정상 종료·저장 마무리를 삭제하지 않습니다.
- feature 추출은 파일별 포함/제외·의존성 분리 후 재사용 처리/계약만 반입합니다. 원본 앱의 Scene·Page·화면 전용 ViewModel/상태·라우팅·앱 DI·업무 흐름·자산은 앱에 둡니다. 사용자 명령은 기능 소유의 의존성·adapter·등록/수명만 자동 연결하고 소비 앱의 화면·업무/DI·동의 UI까지 생성하지 않습니다. 최소 호출자/테스트로 독립 사용과 출력 파일/패치를 검증하며, 분리 불가하면 feature로 등록하지 않습니다. 기존 학습 예제는 유지하고 상세 기준은 각 Composer 내부 작성 규칙을 따릅니다.
- 생성기 소유 파일/관리 구간과 사용자 코드를 분리하고 신규 파일·설정·패키지·연결 충돌을 쓰기 전에 검사합니다. TypeScript와 Flutter의 연결/상태·잠금 방식은 다를 수 있으므로 각 구현을 확인합니다.
- 기존 활성 기능·사용자 변경을 보존합니다. 잘못된 입력/미지원은 중단하고 검증 실패 시 소스·manifest/lock·활성 상태의 복구를 확인합니다. 외부 설치 부작용·캐시·빌드 결과까지 복원됐다고 하지 않습니다. state 해시 편집·일괄 덮어쓰기로 충돌을 우회하지 않습니다.
- 생성 앱의 실행·빌드는 원본 Composer 없이 가능해야 합니다. 소스·설정·테스트·사용 docs·앱 지침·상태·필요 도구를 함께 반출합니다. 현재 두 Composer는 구성품 원본을 앱의 .composer/catalog 또는 .composer/features에 복사하지 않습니다. 기능 추가는 부모 Composer의 뼈대·components를 사용하고 .composer/state.json의 원본 해시·활성 기능·충돌 검사 상태를 앱 Git에 보관합니다.
- 기능 추가 전 생성 당시 부모 원본과의 해시 일치를 검사하고 누락·변경 시 앱 소스·manifest·활성 상태 쓰기 전에 중단합니다. 앱만 옮기면 기능 추가는 사용할 수 없고 Composer 전체를 상대 배치 그대로 옮기면 사용할 수 있습니다. 기존 사본 방식 앱은 자동 전환하거나 사본을 삭제하지 않으며 새 앱과 비교·이행합니다.

## 5. 공통 업데이트·버전·환경

공통 수정은 기준 Composer에서 먼저 구현·검증한 뒤 **선택한** Composer/프로젝트에 반영합니다. 저장소별 적용/미적용·현재 버전 차이를 확인하고 원본 갱신과 기존 앱 이행을 구분합니다.

원본 변경은 해당 저장소에서 fetch 후 전체 log/diff로 확인합니다. 미사용 base·target·feature도 비교하고 로컬 변경을 보존한 뒤 검토한 추적 브랜치를 ff-only로 반영합니다. 이력 분기/충돌은 중단·비교하며 강제 reset·clean·전체 교체를 기본 해결책으로 쓰지 않습니다. 기존 앱은 이전/새 원본과 사용자 코드를 비교·이행·검증하고 코드·lock·원본 식별자·상태·데이터를 함께 보존합니다. 부모 원본 해시는 Git commit과 별개이며 뼈대·구성품의 공개 파일/문서와 루트 생성 도구 변경도 반영합니다. 갱신 전 생성 당시 원본을 보존하고 불일치는 해시만 고쳐 우회하지 않습니다. 기존 사본 방식 앱의 catalog도 보존합니다.

앱·Composer/기능 구현·런타임/SDK·패키지·문서 버전을 구분합니다. 기존 manifest·실제 도구가 생성한 lock·버전 파일을 우선하고 초기 복원 중 일괄 업그레이드·lock 삭제·프로젝트 재초기화를 하지 않습니다. 보안/지원 변경은 공식 근거·영향 버전/노출·조치/보류·담당/재점검 날짜·마지막 정상 조합·데이터 복귀를 기록합니다.

도구 자체·SDK·프로젝트 의존성 갱신을 구분합니다. 기본은 Node nvm/npm, Flutter FVM, Python uv/프로젝트 가상환경, Rust rustup/툴체인 파일이며 기존 프로젝트의 다른 방식을 임의 전환하지 않습니다. macOS는 보조 패키지용 Homebrew를 준비하되 도구별 공식 방식을 우선하고 중복 설치하지 않습니다. 별도 JDK는 brew major formula와 프로젝트 JAVA_HOME으로 선택하며 강제 공용 링크를 기본으로 쓰지 않습니다.

설치·버전 선택·PATH·환경 변수·검증·복귀는 프로젝트 내부 문서와 버전 파일에 기록합니다. 비밀값 없는 .env.example을 공유하고 실제 .env·키·서명·개인 경로·SDK·캐시·설치/빌드 결과는 제외합니다. 전역 기본값을 바꾸지 않으며 공유 설치·키체인·IDE까지 완전히 격리된다고 설명하지 않습니다. 문서 작성은 실제 설치·배포 권한이 아닙니다.

## 6. 추출·신규 제작

추출은 원본 제품을 수정하지 않고 boilerplate-export/유형명/에 독립 결과를 작성합니다. 원본의 실제 관례를 최소 동작으로 축소하고 제품 고유 장비·업무 데이터·화면 순서·비밀값·절대 경로를 일반 샘플에 옮기지 않습니다. 라이선스·저작권은 보존합니다.

신규 제작은 요청한 새 폴더·용도·플랫폼에 맞춰 최소 실행 코드를 만듭니다. 단독형에 Composer·특정 npm 명령을 강제하지 않습니다. 조립형을 요청한 경우에만 생성·기능 연결·소유·충돌·검증/복구 계약을 추가합니다. 관찰 사실·사용자 결정·미검증을 구분하고 없는 출처나 과거 검증을 만들지 않습니다.

결과는 README·번호가 있는 docs·project-agents.md·update.md·실행 소스/설정·버전/lock·테스트를 포함합니다. 지침은 묶음 관리자용과 앱용을 구분하며 AGENTS 적용/출력 방식은 실제 구현대로 안내합니다.

## 7. 문서·도움말·이력

사용자는 내려받기 → help/구성 선택(제공 시) → 생성/가져오기 → 도구/환경·의존성 → 실행/종료 → 검사 → 개발·배포·업데이트 순서로 진행할 수 있어야 합니다. feature 명령이 설치·검사·빌드를 수행한다면 해당 도구 준비를 먼저 안내합니다.

README는 입구, 사용자 docs는 실제 사용, 관리자 docs는 구조·작성·연결·버전 계약을 맡습니다. docs는 01-name.md 순서로 시작·환경/플랫폼·구조/개발·빌드/배포·버전 관리를 연결합니다. 반출 앱 안에서 설치 명령·PATH·버전 선택·설치 확인·실행 위치/권한·예시/실제값·종료를 직접 안내합니다. macOS의 선택 CLT/Xcode 라이선스·최초 초기화는 Git/Homebrew/nvm 전에 확인하고, Windows는 실제 데이터 드라이브 경로를 사용합니다.

형태·feature·용도/버전·명령을 바꾸면 같은 작업에서 묶음/뼈대 README·사용자 가이드·help/compose help·앱 help/README 출력·해당 files/docs·구성품/버전 목록·관리 지침·테스트·update.md를 갱신합니다. 안내 누락은 완료로 보지 않습니다. 구현하지 않은 자동 갱신·제거·target 전환을 안내하지 않습니다.

구조 문서는 실제 파일 역할·공개 계약·허용/금지 의존·정상/오류/종료 흐름·설계 선택을 설명합니다. 빌드/배포는 도구/계정·식별자/버전/lock → 산출물·서명/배포 → 검사·보관·업데이트/복귀를 다룹니다. 개발/빌드 OS·CPU와 사용자 OS/브라우저의 공식 최소/최대 또는 상한 미명시/미확정·실제 검증 최저/최고·근거·확인일을 구분합니다.

변경 문서의 기존 첫 줄 version을 유지하고 설명/링크는 patch, 절차/항목 추가는 minor, 기존 사용법이 바뀌는 구조 변경은 major를 올립니다. update.md의 새 이력은 제목·소개 바로 아래 맨 위에 추가합니다. 커밋 하나당 항목 하나로 묶고 제목은 날짜·커밋 제목으로 작성합니다. 핵심 변경 1~3줄과 검증 결과/미검증 1줄만 기록하며, 호환성·데이터·복귀 주의는 실제 영향이 있을 때만 덧붙입니다. 미커밋 작업은 맨 위 한 항목에서 갱신해 커밋 전에 통합합니다. 같은 날짜도 최신순을 유지하고 중간 작업 과정·긴 로그·반복적인 미커밋 문구는 남기지 않습니다. 기존 이력은 오류 정정 외에는 보존합니다. 공통 작업도 변경된 각 저장소에 기록하며 메인 폴더에서 Git 이력을 만들지 않습니다.

내부 링크는 해당 패키지 안의 상대 경로, 외부 근거는 확인한 공식 주소를 사용합니다. 이동/삭제 전 숨김 파일·들어오는 링크·앵커·실제 설정을 조사합니다. 이모지는 사용하지 않고 긴 로그·중복 설명·문서별 CSS/JS를 추가하지 않습니다. 웹 게시 설정은 실제 보유한 저장소에서만 갱신하며 문서 사이트의 레이아웃 규칙을 실행 샘플에 주입하지 않습니다.

커밋 제목은 type(scope): 한국어 요약 형식으로 작성합니다. type은 feat·fix·refactor·docs·test·build·ci·chore·revert 중 실제 변경 목적에 맞게 선택하고 scope는 변경 영역의 소문자 kebab-case를 사용합니다. 한 커밋에는 한 목적의 코드·검사·문서·update.md를 함께 묶고 독립 저장소는 각각 커밋합니다. 본문은 필요할 때만 이유·실제 검증/미검증·호환성/이행을 짧게 적습니다. 작업 번호·중간 과정·완료 수식어·개인 정보는 제목에 넣지 않습니다. update.md 제목은 날짜와 해당 커밋 제목을 일치시킵니다. 호환성을 깨뜨리는 변경은 type(scope)!:로 표시하고 이행 방법을 본문에 적습니다. Git이 자동 작성한 merge/revert 메시지와 기존 이력은 그대로 두며 커밋·push·이력 재작성은 요청 범위에서만 수행합니다.

## 8. 검증·커밋·보고

- 언어/형태·상태 파일·실제 package scripts에 맞는 기존 검사를 사용합니다. 비자명한 생성/추가/병합 로직에는 작은 재현 검사나 테스트를 남깁니다. 문서 설명만 바꾸기 위해 테스트 도구를 추가하지 않습니다.
- 조립형은 미선택/단독/복수·추가 순서·중복·미지원·잘못된 입력·사용자 변경/충돌·실패 복구와 원본 없는 생성 앱의 실행·빌드를 검사합니다. 현재 두 Composer는 부모 원본에서의 기능 추가·원본 누락/변경 시 무변경 중단·묶음 전체 이동 후 추가·구성품 사본 부재·생성 폴더 Git 제외도 확인합니다. 신규 조립형의 원본 참조 방식은 해당 프로젝트 계약에 맞춰 검사합니다. 외부 의존성을 추가하면 깨끗한 설치도 확인합니다.
- TypeScript/Flutter Composer의 조합 검사는 각 저장소에서 npm run test:compose를 확인해 사용합니다. 실제 타입/분석·테스트·빌드·통신·저장/해제·GUI/기기·플랫폼·권한/서명·배포는 영향 범위와 가능한 환경에 맞춰 수행합니다. 모의 npm/FVM이나 정적 검사를 실제 빌드/배포 성공으로 표시하지 않습니다.
- 상대 링크/앵커·코드 펜스·변경한 JSON/TOML/YAML·실행 명령과 설명의 일치, 개인 파일 포함 여부, **각 변경 저장소의** git diff --check를 확인합니다. 변경된 지침이 생성 앱에도 반영되는지 검사합니다.
- commit 요청이 있으면 저장소별 실제 변경 파일만 선택하고 staged diff·개인 파일·사용자 변경 포함 여부를 확인합니다. 관련 코드·안내·이력을 작업 단위로 묶고 저장소별 commit ID를 보고합니다. 메인 폴더에서 git add .·commit·push를 실행하지 않습니다. 한 저장소의 요청을 다른 저장소의 commit/push 권한으로 확대하지 않습니다.
- 완료 보고에는 대상 저장소·변경/미적용 범위·검사 결과·미검증/남은 위험·요청된 commit/push 여부를 간결히 적습니다. Git 비관리 작업 공간의 AGENTS.md만 바뀌었다면 비관리 파일 변경으로 별도 보고합니다. 못 한 검증·미완료를 전체 성공으로 표현하지 않습니다.

두 Composer의 명령·조립 도구·회귀 검사는 루트 scripts/에 두며 help·compose·workspace는 Composer 루트에서 실행합니다. 뼈대에는 앱 코드와 빌드 도구를 유지하고 생성 앱에는 feature·composer-core·composer-source만 반출합니다. feature는 앱 폴더에서 실행합니다. 스크립트는 compose(생성 CLI)·feature(기능 CLI/잠금/검증)·composer-source(원본 처리)·composer-core(계획/충돌/반영/복구)로 책임을 맞춥니다. 상세 작성·workspace 선택·이행 계약은 각 독립 Composer 내부 문서를 따릅니다. planFeatures는 앱을 변경하지 않고 applyChanges는 검증 성공 후 상태를 기록하며 실패 시 소스·manifest/lock·상태를 복구합니다. 언어별 연결·상태 형식은 해당 내부 계약을 유지합니다.
