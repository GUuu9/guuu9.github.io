# Server-WUI 빌드·운영 배포

[시작 가이드](./getting-started.md)에서 서버·화면을 로컬 검증한 뒤 실제 제품을 배포할 때 읽습니다. 빌드는 개발 PC/CI의 프로젝트 루트, 운영 설정·실행은 배포 서버의 해당 릴리스 폴더에서 수행합니다. 관리 도구 설치는 OS Setup·Tools에서 준비하고 제품의 환경 변수·실행 설정은 해당 프로젝트에서 관리합니다.

현재 샘플에는 인증·TLS·프로세스 관리자·컨테이너·CI 배포 설정이 없습니다. 이 문서는 제품에 구성할 배포 절차와 현재 산출물 경계를 설명합니다. 특정 호스팅·Docker·클라우드 계정을 필수로 가정하지 않습니다. 저장소의 개발 작업 영역 서버를 제품 배포 서버로 간주하지 않습니다.

## 서비스 OS·브라우저 지원 범위

서버가 실행되는 OS와 사용자가 웹을 여는 OS·브라우저를 별도로 관리합니다. 아래 서버 최소값은 `.nvmrc`의 **Node 24.22.1 공식 바이너리 조건**이며 서비스 운영 검증이나 OS 제조사의 보안 지원 보장이 아닙니다.

| 실행 대상 | 최소 OS·조건의 근거 | 최대 지원 OS | 실제 검증 범위·상태 |
| :--- | :--- | :--- | :--- |
| GNU/Linux 서버 x64·arm64 | kernel 4.18 이상·glibc 2.28 이상. 네이티브 의존성이 추가 조건을 요구할 수 있음 | 공식 숫자 상한 미명시. 서비스 배포판별 상한 미확정 | Linux 운영 배포 미검증 |
| Windows 서버 x64 | Node 기준 Windows 10 / Server 2016 이상 | 공식 숫자 상한 미명시. 서비스 상한 미확정 | Windows 서버 운영 미검증 |
| macOS 개발·로컬 실행 x64·arm64 | Node 공식 바이너리 기준 macOS 13.5 이상 | 공식 숫자 상한 미명시. 서비스 상한 미확정 | 기존 macOS 13 x86_64 로컬 검사 기록만 있음. 정확한 OS patch는 해당 기록에 없음 |
| 웹 사용자 OS·브라우저 | 서비스 최소 OS·브라우저 버전 미확정. Vite 출력과 실제 사용하는 Web API의 교집합 확인 필요 | 최고 검증 OS·브라우저 미기록 | 실제 브라우저 동작 미검증. 서버 Node의 OS 범위를 사용자 OS 범위로 사용하지 않음 |

서버 조건의 근거: [Node 24.22.1 Platform list](https://github.com/nodejs/node/blob/v24.22.1/BUILDING.md#platform-list). 예시 배포판 이름을 그대로 지원 정책으로 선언하지 않고 현재 보안 지원 중인 배포판·CPU·libc와 실제 의존성을 검증해 운영 대상을 정합니다. 컨테이너를 쓰면 호스트 kernel과 이미지 내부 배포판·libc를 구분합니다.

브라우저용 샘플은 Vite 8.3.5의 기본 build target을 사용하고 명시적인 서비스 브라우저 정책은 없습니다. [Vite 프로덕션 호환성 안내](https://vite.dev/guide/build)는 구문 변환 범위이며 모든 Web API의 polyfill을 제공하지 않습니다. 예를 들어 현재 Api의 AbortSignal.timeout도 대상 브라우저에서 확인해야 합니다. 브라우저가 해당 OS에서 설치·갱신 가능한지까지 포함해 Chrome·Edge·Firefox·Safari의 실제 시험 버전을 기록합니다.

Node·Vite·브라우저 API·패키지 변경 시 서버 최소 OS와 웹 사용자 최소 OS를 각각 검토합니다. 최신 OS나 최신 브라우저를 시험하지 않았다면 최대 지원 버전으로 선언하지 않습니다.

## 1. 빌드 산출물과 버전 확정

Node·npm과 package-lock.json을 기존 정상 조합으로 복원한 프로젝트 루트에서 실행합니다.

```bash
npm ci
npm run check
npm test
npm run build
```

| 경로 | 역할·배포 시 주의 |
| :--- | :--- |
| `dist/server/` | 컴파일된 서버 JS와 복사된 config. 실행 진입점 `dist/server/index.js` |
| `dist/webui/` | Vite 정적 HTML·JS·CSS. 이 프로젝트의 출력은 Vite 기본 `dist/`와 다름 |
| package.json·package-lock.json | 앱 버전·런타임 의존성 복원 기준 |
| 런타임 node_modules | 서버의 Express 등 외부 의존성. 개발 PC의 폴더를 다른 OS로 복사하지 않음 |

현재 서버는 빌드된 `dist/webui/`도 정적으로 제공합니다. 운영 후보를 동일 OS/CPU의 별도 릴리스 폴더에서 검증할 때 package 파일·dist를 함께 배치하고 일반 사용자 권한으로 `npm ci --omit=dev` 후 `npm start`로 실행할 수 있습니다. 빌드 도구는 개발 의존성이므로 **빌드 전에** omit하지 않습니다. 기존 운영 폴더에서 npm ci를 실행해 서비스 의존성을 중간 교체하지 않습니다.

앱 package 버전만으로 배포를 식별하지 않고 소스 커밋·잠금 파일·Node/npm·OS/CPU·산출물 체크섬·환경 이름을 함께 기록합니다. 이미지 배포를 선택하면 고유 태그와 digest를 기록합니다. 같은 릴리스 식별자를 다른 내용으로 덮어쓰지 않습니다.

## 2. 서버·웹 연결과 운영 환경

샘플은 `127.0.0.1`에 바인딩하고 기본 API 포트는 3101입니다. 현재 설정·변수의 실제 지원 범위는 [샘플 설명서](./boilerplate.md)를 확인합니다. `.env` 파일을 두는 것만으로 Node가 자동 읽는 것은 아닙니다. 필요한 변수는 `.env.example`에 이름·예시를 공유하고 프로세스 관리자·CI·실행 스크립트에서 실제 값을 전달하도록 제품에 구현·기록합니다.

| 배포 형태 | 연결 구성 |
| :--- | :--- |
| 서버가 웹도 제공 | 현재 Express 정적 제공 구조 유지. 같은 호스트의 reverse proxy가 HTTPS 요청을 localhost API/웹 포트로 전달 |
| 웹을 CDN/정적 호스팅에 분리 | `dist/webui/` 게시와 `/api`의 서버 전달 경로를 별도 구성. Vite 개발 proxy가 운영에서도 동작한다고 가정하지 않음 |
| 컨테이너 선택 | 내부 listen 주소·서비스 포트·외부 공개 범위·볼륨·상태 검사를 제품 설정으로 정의. 현재 localhost 바인딩을 그대로 두면 컨테이너 외부에서 접근할 수 없음 |

현재 브라우저 Api는 같은 origin의 `/api`를 호출합니다. API를 다른 origin으로 옮기려면 프런트 URL 설정·CORS·인증 정책을 함께 구현해야 합니다. 하위 URL 경로에 웹을 게시하면 Vite base·asset 경로와 실제 API 경로를 함께 검증합니다. SPA 클라이언트 라우팅을 도입했을 때만 새로고침 fallback을 구성하고 `/api` 오류를 index.html로 바꾸지 않습니다.

Vite `dev`·`preview`를 운영 서버로 사용하지 않습니다. [Vite 정적 배포](https://vite.dev/guide/static-deploy) · [Vite 환경 변수](https://vite.dev/guide/env-and-mode). 브라우저 번들에 포함되는 값은 공개됩니다. `VITE_*`나 정적 JSON에 서버 토큰·DB 비밀번호를 넣지 않습니다.

## 3. 배포 준비 → 시험 배포 → 운영 전환

1. 서버 관리자와 도메인·DNS·인증서·HTTPS 종료 위치·방화벽·프로세스 실행 계정·로그 보관을 정합니다. reverse proxy를 쓰면 신뢰할 proxy 범위와 Express 설정을 검토합니다.
2. 인증·접근 제어·요청 제한·비밀 주입·로그의 민감정보 처리를 실제 제품 요구에 맞게 구현합니다. 샘플 로컬 API를 그대로 인터넷에 노출하지 않습니다.
3. 같은 OS/CPU·Node 조건에서 릴리스 폴더 또는 이미지를 만들고 프로세스 관리자/호스팅 서비스의 시작·재시작·종료·상태 확인을 구성합니다. `NODE_ENV=production` 등 실제 지원 설정을 실행 프로세스에 적용합니다.
4. 시험 환경에서 페이지·정적 자산·API 정상/오류·직접 URL 접근·HTTPS·권한·재시작을 검사합니다. 제품의 실제 상태 확인 경로를 정의하며 샘플에 health endpoint가 있다고 가정하지 않습니다.
5. 운영 전환 전 현재 릴리스·환경 설정·영구 데이터와 복귀 수단을 보존합니다. 새 릴리스로 트래픽을 전환하고 서버 오류·응답 지연·화면의 API 연결을 확인합니다. CI의 파일 업로드 성공만으로 완료 처리하지 않습니다.

[Express 운영 권장 사항](https://expressjs.com/en/advanced/best-practice-performance/)에 따라 프로세스 감독·reverse proxy 등 필요한 구성을 선택합니다. 구체적인 서비스 등록·배포 명령은 선택한 운영 환경이 정해졌을 때 그 프로젝트에 기록합니다. 아직 없는 배포 스크립트를 실행 가능한 명령으로 제시하지 않습니다.

## 4. 웹 캐시·데이터·업데이트·복귀

서버와 웹을 같은 릴리스 단위로 관리합니다. 분리 배포라면 구·신 웹과 API의 호환 범위를 정하고 전환 중 혼합 버전도 검사합니다. 해시가 있는 JS/CSS 자산과 HTML의 캐시 정책을 구분하며 CDN에 남은 구 HTML이 필요한 자산을 먼저 지우지 않습니다.

현재 샘플에는 DB·업로드 저장소가 없습니다. 제품에 추가하면 영구 데이터를 dist·릴리스 폴더·컨테이너 쓰기 영역과 분리하고 백업·복원·마이그레이션 절차를 배포 전에 작성합니다. 이미지/소스 복귀만으로 데이터 스키마가 되돌아오지는 않습니다.

업데이트는 새 릴리스 폴더/이미지에 복원·검증한 뒤 전환합니다. 실패하면 보존한 이전 실행 단위·환경으로 되돌리고 API·웹·데이터 호환을 확인합니다. 이전 산출물·런타임·정적 자산은 복귀와 캐시 만료에 필요한 기간 동안 보존합니다. 전체 볼륨 삭제·잠금 파일 삭제·공유 Node 변경을 복구 첫 단계로 사용하지 않습니다.

확인일: 2026-11-03. 실제 package 스크립트·Vite 출력·Express 정적 제공과 listen 설정을 확인했습니다. 의존성 설치·외부 배포·HTTPS·운영 전환·복구 실행은 이번 작업에서 검증하지 않았습니다.

OS 범위 확인일: 2026-11-03. 저장소 설정과 고정 버전의 공식 근거를 대조했으며 최소·최대 OS에서 새 실행 검증은 수행하지 않았습니다.
