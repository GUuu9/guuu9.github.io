# 보일러플레이트 추출·신규 작성 규칙

이 문서는 **기존 프로젝트에서 보일러플레이트를 추출하거나 새로운 보일러플레이트를 제작할 때** 사용하는 공통 기준입니다. 기존 Composer의 base·target·feature 추가/수정은 각 Composer 내부 작업 지침을 따르며 여기서 상세 계약을 중복 관리하지 않습니다.

## 1. 작업 유형·범위

| 작업 | 적용 기준 |
| :--- | :--- |
| 기존 프로젝트 추출 | 원본의 실제 구조·동작을 최소 독립 샘플로 축소. 원본 제품은 변경하지 않음 |
| 신규 보일러플레이트 제작 | 요청한 용도·언어·실행/배포 환경에 맞는 최소 동작과 문서·검사를 작성 |
| 기존 Composer 확장 | [TypeScript Composer](https://github.com/GUuu9/typescript-composer) 또는 [Flutter Composer](https://github.com/GUuu9/flutter-composer)의 내부 지침 적용 |

작업 전에 유형·목적·단독 실행형/조립형·대상 플랫폼·출력 위치·기존 자료를 확인합니다. 신규 제작을 기존 Composer 확장으로 강제하거나 단독 샘플에 생성기를 추가하지 않습니다. 조립형과 자동 기능 추가는 요청한 경우에만 구현합니다.

원본 프로젝트에서 추출할 때 결과는 boilerplate-export/유형명/ 안에 작성합니다. 원본 루트 README·AGENTS·제품 코드·의존성/lock·CI·배포 설정과 사용자 변경은 보존합니다. 신규 제작은 사용자가 지정한 새 작업 폴더에서 시작하며 기존 폴더가 있으면 먼저 조사합니다. 결과 코드는 별도 보일러플레이트 저장소에서 관리하고 이 문서 저장소에 복제하지 않습니다. commit·push·배포는 요청된 범위에서만 합니다.

## 2. 조사·최소 동작

추출은 Git 상태·대표 기능의 연결된 코드·호출자·테스트·설정·manifest/lock·실행/오류/종료 흐름을 읽고 실제 반복 관례를 선택합니다. 관찰한 사실·사용자 결정·미확인을 구분하고 접근하지 못한 자료를 추측하지 않습니다.

신규 제작은 사용 시나리오·실행 환경·지원 범위를 먼저 정하고 필요한 언어/도구만 선택합니다. 원본이 없는데 출처나 과거 검증을 만들어 쓰지 않습니다.

대표 흐름 하나가 실제 동작해야 합니다. 제품 고유 장비·업무 모델·패킷·화면 순서·개인 데이터·절대 경로·비밀값을 일반 샘플에 옮기지 않습니다. 빈 API·Model·Service·Repository·util/core를 형식 때문에 추가하지 않고 기존의 유효한 패턴을 재사용합니다. 외부 자산의 라이선스·저작권은 유지합니다.

## 3. 독립 패키지·구조

| 형식 | 결과 계약 |
| :--- | :--- |
| 단독 실행형 | 유형 폴더가 프로젝트 루트. README·docs·project-agents·update와 실행 소스·설정·버전/lock·테스트를 함께 포함 |
| 조립형 | 묶음 루트의 관리/생성 안내와 뼈대·구성품을 구분. 생성 앱은 독립 루트에 코드·도구·설명·지침·상태를 포함 |

단독 실행형에 components·compose·feature 명령이나 특정 npm 인터페이스를 강제하지 않습니다. 조립형을 요청했다면 결과 형태·기능·선행/충돌·파일 소유·버전 계약과 자동 연결·검증/복구를 함께 설계합니다. 기존 Composer의 구현 세부를 공통 표준처럼 복제하지 않습니다.

유형 폴더 하나를 새 위치로 옮겨도 설치·실행·빌드는 원본 제품·다른 프로젝트·개인 경로에 의존하지 않아야 합니다. 조립형의 기능 추가에 필요한 원본 위치·식별자·검사·이동 제약은 실행 의존성과 구분해 명시합니다. 실제 .env·키·서명·SDK·캐시·의존성 설치 결과·빌드 결과는 제외하고 필요한 공개 설정·.env.example·버전 파일·도구가 생성한 lock은 포함합니다. 언어/생성 방식상 첫 설치 때 lock을 만드는 경우 그 이유와 보관/후속 복원 방법을 명시합니다. lock 삭제·수작업 편집을 복원 절차로 쓰지 않습니다.

현재 TypeScript/Flutter Composer는 앱을 묶음의 project/ 아래에 두고 부모의 뼈대·components에서 기능을 추가합니다. 앱에는 구성품 원본 사본 없이 .composer/state.json의 원본 해시·활성 기능·충돌 검사 상태와 도구를 보관합니다. 고정 `/project/*`·`!/project/.gitkeep` 규칙으로 새 앱을 제외하고 앱 Git은 별도로 관리합니다. 부모 원본 누락·변경은 추가 전에 중단하며 앱만 이동하면 기능 추가는 불가합니다. 신규 조립형에 이 구현을 자동 강제하지 말고 요청한 사용 방식에 맞춰 원본 참조 계약을 정합니다.

입력·경로·발신자 검증과 안전한 오류·시작 실패·정상 종료·해제·데이터 보존을 유지합니다. 조립 도구가 파일을 바꾸면 사용자 파일과 생성기 소유 파일을 구분하고 충돌 시 쓰기 전에 중단합니다. 실패 복구 범위와 외부 설치 부작용·캐시/산출물의 한계를 명시합니다.

## 4. README·사용 안내

README는 목적·최소 동작·버전 기준·선행 조건·빠른 시작·실제 구조·검사·상세 문서·제약의 입구입니다. 원본 제품 README를 복제하지 않습니다. 흐름은 **다운로드/가져오기 → 도구·프로젝트 환경 → 의존성 복원 → 실행/종료 → 검사 → 개발·배포·업데이트**입니다. 조립형만 생성/기능 추가 단계를 해당 도구 준비 뒤에 넣습니다.

설치·PATH·버전 선택·상태 확인·실행 위치/권한·실제값/예시·포트/기기·종료를 직접 안내합니다. 반출 패키지 밖 Setup·Tools를 전제로 하지 않고 공식 링크는 다운로드/근거 확인에 사용합니다. 명령은 해당 셸의 코드 블록에 둡니다. 자동화하지 않은 수동 작업을 자동 완료로 표현하지 않습니다.

공통 필수·조건부 필수·선택 도구와 준비 순서/완료 확인을 구분합니다. macOS는 Git·Homebrew·nvm 전에 선택한 CLT 또는 전체 Xcode의 라이선스·최초 초기화를 확인하며 불필요한 전체 Xcode·SDK는 요구하지 않습니다. Windows는 실제 데이터 드라이브 경로를 안내하고 프로젝트 때문에 전역 도구 기본값을 바꾸지 않습니다.

실제 제공하는 help·명령·환경·기능을 바꾸면 README·시작 가이드·관련 사용 문서·도움말을 같은 작업에서 갱신합니다. 안내 누락은 완료로 처리하지 않습니다. 문서 수를 늘리기보다 책임별 한 곳에 상세 절차를 두고 연결합니다.

## 5. 구조 문서·지침·배포

docs는 01-name.md 순서로 시작·환경/플랫폼·구조/개발·빌드/배포·버전 관리를 안내합니다. 조립형은 관리자 docs와 생성 앱 docs를 구분하고 앱 문서는 앱 안에서 링크가 해결돼야 합니다.

구조 설명은 적용 범위·버전·직접 관리 파일의 역할/명명·의존/흐름·기능 작성·명령·보안/변경 경계·새 앱 적용·검증을 담습니다. 다음 아키텍처 항목을 실제 코드로 설명하며 짧은 기능 문서마다 복제하지 않습니다.

- 구성·실행 경계와 상태/데이터 소유
- 폴더/계층의 책임·공개 계약·허용/금지 의존
- 진입·DI/객체 조립·시작 실패·수명/해제
- 대표 입력부터 정상/오류 응답·화면까지의 전체 흐름
- 실제 경로의 의존/흐름도와 설계 선택 이유. import와 HTTP/IPC 실행 호출 구분

project-agents.md는 대상 프로젝트의 작업 지침 보관본입니다. 범위·작업 전 확인·구조/명명/경계·최소 완결 구현/보안·실제 검사·완료/한계를 담고 작업 종류별 선행 문서와 갱신/검사를 안내합니다. 단독형은 적용 시 AGENTS.md로 사용하는 방법, 조립형은 관리자/앱 지침 구분과 생성 시 출력 방식을 실제 구현대로 적습니다.

빌드/배포 문서는 도구/계정·식별자/버전/lock → 실제 명령/산출물 → 서명·스토어/운영 배포 → 검증·보관·업데이트·복귀 순서입니다. 개발/빌드 OS·CPU와 사용자 OS·브라우저를 구분해 공식 최소/최대 또는 상한 미명시/미확정, 실제 검증 최저/최고, 고정 SDK 근거·확인일을 적습니다. 로컬 빌드를 실제 배포·지원 보장으로 표시하지 않습니다.

## 6. 버전·보안·업데이트

앱·보일러플레이트/구성품 구현·도구/SDK·패키지·문서 버전을 구분합니다. 실제 manifest·lock·버전 파일을 기준으로 초기 복원에 일괄 업그레이드를 섞지 않습니다.

보안/지원 이슈는 공식 근거·영향 버전/노출·조치/보류 이유·담당/재점검 날짜를 남깁니다. 정상 조합은 원본 revision/스냅샷·선택 구성·lock·도구·OS/CPU·검사 결과로 식별하고 과거 통과/실패와 마지막 정상 복귀 기준을 보존합니다.

update.md는 제목·소개 바로 아래 맨 위에 최신 이력을 추가하고 같은 날짜의 새 작업도 기존 항목 위에 둡니다. 이유·범위·확정 commit·버전 전후/미변경·적용/복귀/데이터 영향·실제 검사/미검증을 적고 검증은 해당 작업의 하위 절로 묶습니다. 코드 저장소에서 관리하며 안내 저장소에 이력을 복제하지 않습니다.

보일러플레이트 원본 갱신과 이미 개발한 앱의 반영은 별개입니다. 기존 앱을 보관하고 이전/새 원본과 사용자 코드를 비교·검증·이행하도록 안내합니다. 기존 앱을 통째로 덮어쓰거나 구현하지 않은 자동 업데이트를 약속하지 않습니다.

부모 원본 참조 방식은 생성 당시 원본 해시와 필요한 파일을 함께 보존합니다. 공개 파일·문서 변경도 해시 불일치를 일으킬 수 있으므로 원본을 복원하거나 새 앱으로 비교·이행하며 state 해시만 고쳐 우회하지 않습니다. 기존 사본 방식 앱의 도구·상태·원본 사본은 자동 삭제/전환하지 않습니다.

## 7. 완료 확인·보고

- 별도 위치에 복사해 원본 없이 설치·실행·종료·분석/타입·테스트·빌드를 확인합니다. 의미 있는 작은 검사를 포함하고 설치/실행에 운영 자격증명·데이터를 요구하지 않습니다.
- 조립형은 제공한 help·생성·기능 미선택/단독/복수·순서·중복·사용자 변경 보호·충돌·실패 복구와 원본 참조 계약에 맞는 기능 추가도 검사합니다. 부모 참조형은 원본 누락/변경 시 앱 보존·묶음 전체 이동 후 추가·구성품 사본 부재·생성 폴더 Git 제외를 확인합니다.
- 새 의존성은 깨끗한 설치로 확인하고 모의 명령·정적 검사·실제 실행·GUI/기기·권한·서명·배포·다른 OS를 구분합니다. 못 한 검사는 조건/이유를 남깁니다.
- 파일 역할/소유/계약·명령과 설명, 반출 후 상대 링크/앵커·코드 펜스·설정 문법·git diff --check를 확인합니다. 개인 설정·키·캐시·산출물 포함 여부를 검사합니다.
- 검증 문서에 요구사항 / 실제 파일·절 / 검증 결과 / 상태(충족·미충족·미검증·해당 없음)를 기록합니다. 테스트 통과로 문서 누락을 충족 처리하지 않습니다.
- 최종 보고에는 결과 폴더/대상 저장소·실제 변경·추출 시 원본 제품 미변경 여부·환경/명령/결과·미충족/미검증·데이터/복귀 영향을 적습니다. 불완전한 결과를 전체 완료로 보고하지 않습니다.

기존 Composer 확장은 각 독립 저장소의 규칙을 사용합니다. 이 문서 저장소에는 추출/신규 제작 안내만 두고 이동된 Composer 소스를 복구하거나 복제하지 않습니다.
